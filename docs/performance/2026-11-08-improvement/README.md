# 自己ループとスタイル再計算の改善

2026-11-08 に、基準コミット `a5c9f8f` と改善後の `4f2026a` を比較しました。普段の Chrome プロファイルは使わず、一時プロファイルの Chromium 158 / macOS で確認しています。

## 変更内容

`f36491f` と `4f2026a` で、サイト本来の色の CSSTransition が終了またはキャンセルされるのを待ってから、シートを切り替えるようにしました。その切り替えで新しく生じた色の遷移だけをキャンセルし、`transitionend` による自己ループと、色を読む際の中間色の混入を防ぎます。通常 DOM と Shadow DOM の両方を対象にします。

既存 Animation オブジェクトとの比較だけでは、シート切り替えでブラウザが遷移を作り直す場合に保護できませんでした。元の inline `!important` の文字色を変える回帰テストで、完了通知が失われる不具合を確認し、遷移の終了を待つ方式に修正しています。

透明度・位置など配色以外の遷移はキャンセルしません。イベントの伝播やサイト全体のトランジションを無効にする方法も使っていません。拡張の切り替えで生じる色の遷移は滑らかに再生せず、最終色へ反映します。

`a803b98` で、同じ配色の要素は疑似要素も含めて CSS ルールを共有するようにしました。1 要素に 1 ルールを作る方式で増えていたセレクター照合を減らします。生成した CSS が前回と同じ場合は `replaceSync` も省きます。色変換の式、パレット、設定、Sheets の Canvas 処理は変更していません。

## 制御したページの比較

ON のメインスレッドのタスク時間は、マウス移動中に約 88%、文字入力中に約 88% 減りました。スタイル再計算はマウス移動中に 3,996 ms から 82 ms へ減っています。

| 操作                    | タスク時間 改善前 → 後 | 操作列の所要時間 改善前 → 後 | Long Task 数 改善前 → 後 |
| ----------------------- | ---------------------: | ---------------------------: | -----------------------: |
| 静止                    |             24 → 15 ms |             2,203 → 2,202 ms |                    0 → 0 |
| マウス移動 20 回        |         4,725 → 560 ms |             4,927 → 2,230 ms |                   20 → 0 |
| 100 ms ごとの文字列更新 |         2,143 → 585 ms |             2,317 → 2,204 ms |                    9 → 0 |
| 16 文字の入力           |         3,811 → 474 ms |             4,227 → 1,809 ms |                   16 → 0 |

表の Long Task 数も中央値です。改善後の文字列更新の 1 試行では、57 ms の Long Task が 1 回ありました。操作中のフレーム間隔 p95 は 233 ms から 33 ms へ減りました。OFF のマウス移動中のタスク時間は改善前 52 ms、改善後 36 ms、未導入では 45 ms、35 ms でした。対照条件に比べて ON の処理はまだ多く残っています。

この制御ページは色のトランジションを指定していないため、静止中の自己ループは改善前も発生しません。自己ループの対策はトランジションの検証ページと公開サイトで別に確認しています。

操作列には各 100 ms の待ちを含むため、所要時間を人間の入力遅延そのものとは扱いません。タスク時間はメインスレッドで処理した時間の累積で、PC 全体の CPU 使用率ではありません。

### 測定条件

3,014 要素の [再現ページ](http://127.0.0.1:4175/?cards=600) を使い、各バンドルで ON / OFF / 未導入をそれぞれ 3 回ずつ測りました。OFF → ON → 未導入、ON → 未導入 → OFF、未導入 → OFF → ON の順番です。表は 3 回の中央値です。基準コミットを `git archive` で別ディレクトリへ展開してビルドし、以前の調査記録のソース・バンドルの SHA-256 と一致することを確認しました。

同じ調査スクリプト、1280 × 900、headless、ライト配色、1 MiB のディスクキャッシュ上限を使い、並列実行を避けています。改善前の全試行の後に改善後を測っているため、PC の状態変動を完全には除けません。OFF・未導入の対照値も JSON に記録しています。

```sh
# 基準コミットを別ディレクトリでビルドしてから、そのルートを指定する
node scripts/profile-performance.mjs --large --project=基準ディレクトリ --output=test-results/before
node scripts/profile-performance.mjs --large --output=test-results/after
```

通常の再現ページは `node scripts/profile-performance.mjs --serve` で起動できます。サーバー停止中は URL にアクセスできません。

記録: [改善前の全 9 試行](before/large-results.json)、[改善後の全 9 試行](after/large-results.json)。プロファイルとトレースは比較区間とは別に採取しています。

## 公開サイト

[Wikipedia / Color](https://en.wikipedia.org/wiki/Color) と [公開 Google Sheets サンプル](https://docs.google.com/spreadsheets/d/1BxiMVs0XRA5nFMdKvBdBZjgmUUqptlbs74OgvE2upms/edit) を、それぞれ OFF → ON → OFF で確認しました。

| ON の測定区間             | Wikipedia |   Sheets |
| ------------------------- | --------: | -------: |
| 静止約 2.5 秒のタスク時間 |     86 ms |    97 ms |
| 静止約 2.5 秒の再走査     |      0 回 |     0 回 |
| マウス移動の所要時間      |  3,140 ms | 2,326 ms |
| マウス移動のタスク時間    |  1,588 ms |   321 ms |

追加の約 5 秒のイベント観測でも、両サイトの ON で色の `transitionend` と再走査はともに 0 回でした。診断用のイベント遮断を入れる前の値です。Wikipedia は 5,005 ms 中 154 ms、Sheets は 5,005 ms 中 284 ms のタスク時間でした。サイトの DOM 更新があれば、その後の再走査は引き続き行われます。

昼の改善前調査では、Wikipedia のマウス移動は 7,491 ms、静止中にも再走査が反復していました。今回の ON は 3,140 ms です。ただし公開サイトの改善前後は測定時刻が異なり、Sheets の DOM 要素数も約 1,770 から約 1,900 に変わっています。この比較は参考値とし、改善率の根拠には制御ページの反復測定を使います。

Wikipedia のマウス移動中には最長約 94 ms、中央値約 81 ms の Long Task がまだ発生します。静止中の自己ループは解消していますが、大きいページでの全走査の負荷は残っています。

記録: [公開サイトの全測定](after/live-results.json)、[Wikipedia の約 5 秒の観測](after/wikipedia-on-feedback.json)、[Sheets の約 5 秒の観測](after/sheets-on-feedback.json)。表示は [Wikipedia](after/wikipedia-on-1.png)、[Sheets](after/sheets-on-4.png) の画像でも確認しました。

ホイール操作も JSON にありますが、この計測ではスクロール距離を判定していないため、スクロールの正しさの保証には使いません。セル選択・スクロールの実操作確認は [実サイトの検証](../../verification/README.md) と分けています。最終版の再確認では名前ボックスが A2 から A3 に変わり、ホイール操作後に Canvas の描画ハッシュが変わることを検証しました。

`pnpm verify:sites` の初回は GitHub の接続が `ERR_HTTP2_SERVER_REFUSED_STREAM` で失敗しました。新しい一時ブラウザでの再実行では、Sheets・GitHub・Wikipedia・Example Domain の全 4 サイトで HTTP 200、ページの JavaScript エラー 0 件、配色と実操作の判定が通っています。[初回の記録](site-verification-first.json) も残しています。旧内部属性に依存していた診断用の `themed` 件数は検証スクリプトから削除し、配色は背景・文字の色と Canvas のピクセルで判定しています。

## 回帰の確認

`pnpm check` の型検査・単体テスト 32 件・フォーマット確認と、`pnpm test:e2e` の 15 件が通っています。既存の 12 件は判定を変更せず、次の 3 件を追加しました。

- 配色の適用だけではサイト側の操作完了通知が出ず、利用者が透明度や元の文字色を変えた後には本来の完了通知が出る
- 同色の面の片方だけ変更しても、隣の面や異なる色の疑似要素を巻き込まず、変更の解除で元の配色へ戻る
- 色の遷移を途中でキャンセルしても、後から追加された面を暗くして読みやすくできる

いずれも通常 DOM と Shadow DOM で確認します。最初のテストは基準バンドルで『操作待ち』が『未操作の色変更』になるアサーション失敗を確認し、失敗した判定の期待値を変えずに、修正後の通過を確認しました。2 件目は CSS 共有による表示の巻き込みを検知するためのテストで、基準バンドルでも通ります。実装の内部属性やルール数は合否に使いません。

詳細は [テストの目的](../../testing.md)、検証ページは [transitions.html](http://127.0.0.1:4173/transitions.html) です。検証ページを開くには `node tests/server.mjs` を起動してください。

## 残る制約

操作時の全 DOM 走査と、元の色を読むためのシートの無効化・有効化は残っています。要素数や個別の配色が多いサイトでは負荷が出る可能性があります。今回の改善は全サイトで一定の時間内に動作する保証ではありません。

色の滑らかなトランジションや、その完了・キャンセルのイベントに依存するサイト側の振る舞いについては、個々のサイトでの互換性確認が必要です。サイト本来の色の遷移が一時停止・反復して終了しない間は、再解析も待機します。色の遷移完了を待つため、動的な要素のダーク表示への追従が遅れる場合があります。

公開 Sheets は閲覧専用の小さいサンプルです。実サービスでの編集・数式入力、個人の大規模シート、長時間利用、他の拡張との組み合わせは未確認です。普段の Chrome に反映するには、`chrome://extensions` で拡張を更新し、対象ページを再読み込みしてください。Sheets では保存状態を確認してから再読み込みします。

[改善前の原因調査](../2026-11-08/README.md) は当時の実装と測定の記録として残しています。`dark-engine:render` は今回のアニメーション確認による同期的なスタイル反映も含むようになったため、以前の値との単純比較には使いません。表では処理範囲が同じ DevTools の TaskDuration を比較しています。
