# 操作時の負荷調査

2026-11-08、リポジトリの作業ツリーと一致する `dist` を、一時プロファイルの Chromium 158.0.8127.18 で測定しました。普段の Chrome の設定・拡張には変更を加えていません。本番コードの最適化も行っていません。

## 結論

この拡張を ON にすると、要素数の多いページでマウス移動や文字入力が重くなる現象を再現できました。主因は全 DOM の再走査と CSS の全置換、それに伴うブラウザのスタイル再計算です。さらに Wikipedia と公開 Sheets では、配色の再適用で生じる `transitionend` が次の再走査を予約する自己ループを、コードと対照実験から確認しました。色変換関数の時間だけでは、実際の操作負荷を評価できません。

静止した検証ページでは差は小さく、すべてのページ・操作で同じ負荷が出るという結果ではありません。利用者が重さを感じた具体的な URL は未確認です。長時間利用時のメモリリークや、個人プロファイルにある他の拡張との組み合わせも未調査です。

## 比較方法

- macOS / arm64、14 コア、メモリ 64 GiB。headless、1280 × 900、ライト配色。一時プロファイルを使い、並列実行しません。
- 未導入、導入済み OFF、導入済み ON を比較します。OFF はポップアップと同じ `chrome.storage.local` の設定を使い、ページを読み込む前に保存します。
- 100 枚 / 600 枚のカードを置き、DOM 要素数は 514 / 3,014。画面外の要素も含みます。
- 各規模で 3 回ずつ、OFF → ON → 未導入、ON → 未導入 → OFF、未導入 → OFF → ON の順番で実行します。
- 読み込み後に 2.2 秒以上待ち、静止 2.2 秒、20 回のマウス移動、100 ms ごとの文字列更新、16 文字の入力を測定します。移動・入力には各 100 ms の待ちを含み、操作列の所要時間は人間の入力遅延そのものではありません。文字列更新の頻度は予約値で、メインスレッドが塞がると実際の更新は遅れます。
- DevTools Protocol の `Performance.getMetrics`、PerformanceObserver、requestAnimationFrame を同じ条件で使います。`TaskDuration` は測定区間中のメインスレッドのタスク時間であり、PC 全体の CPU 使用率ではありません。
- Long Task は 50 ms 以上のメインスレッドのタスクです。操作への影響を測る補助指標に使い、Web Vitals の INP と同一視しません。フレーム間隔の p95 も実ディスプレイの FPS ではありません。
- 起動直後の変換は測定区間の対象外です。JSON の `startupMs` は読み込みと待機を含む参考値です。

最初の実行は 514 要素の全 9 試行を保存後、容量不足で停止しました。3,014 要素は `--large` で再実行しています。再実行と公開サイト検証では全モードに同じ `--disk-cache-size=1048576` を指定し、一時ディスクキャッシュを制限しました。初回の 514 要素と予備測定ではこの指定をしていません。

## 制御したページの結果

マウス移動中のメインスレッドのタスク時間と停止の比較です。

| 要素数 | 未導入 |   OFF |       ON | ON の Long Task 数 | フレーム間隔 p95（OFF → ON） |
| ------ | -----: | ----: | -------: | -----------------: | ---------------------------: |
| 514    |  31 ms | 38 ms |   236 ms |                  0 |                   17 → 17 ms |
| 3,014  |  46 ms | 45 ms | 4,751 ms |                 20 |                  17 → 233 ms |

各セルは 3 回の中央値です。フレーム間隔と Long Task 数は各試行の値を集計しています。未導入と OFF が近く、ON の操作中にだけ大きな差があることから、単なる PC 全体の高負荷だけでは説明できません。

3,014 要素での同じ操作列の所要時間です。静止・更新は時間を指定した区間のため、負荷が高くても所要時間だけでは影響が見えません。

| 操作                    | OFF の所要時間 | ON の所要時間 | OFF のタスク時間 | ON のタスク時間 | ON の Long Task 数 |
| ----------------------- | -------------: | ------------: | ---------------: | --------------: | -----------------: |
| 静止                    |       2,203 ms |      2,205 ms |            19 ms |           21 ms |                  0 |
| マウス移動 20 回        |       2,296 ms |      4,933 ms |            45 ms |        4,751 ms |                 20 |
| 100 ms ごとの文字列更新 |       2,205 ms |      2,326 ms |            73 ms |        2,151 ms |                  9 |
| 16 文字の入力           |       1,690 ms |      4,268 ms |            88 ms |        3,830 ms |                 16 |

ON の操作中は 1 回あたり約 235 ms の Long Task が続きます。マウス移動中は測定時間の約 96% をメインスレッドのタスクが占めています。文字列更新のように見た目の色が変わらない更新でも、全再走査が予約されます。

## コードとトレースの対応

[src/engine/dom-engine.ts](../../../src/engine/dom-engine.ts) は `pointerover` / `pointerout`、入力、フォーカス、DOM の属性・文字列・子要素の更新などから、ページ全体の再走査を予約します。開始間隔の下限は 150 ms ですが、処理自体が長い場合の上限にはなりません。

再走査では、自分のスタイルシートを無効にして全表示要素の computed style と疑似要素を読み、要素ごとのルールを作り直し、`replaceSync` とシートの有効化を行います。色のキャッシュが命中しても、DOM 読み取りと CSS 再適用は残ります。

3,014 要素のマウス移動区間では、ON のタスク時間 4,751 ms のうちスタイル再計算が 4,038 ms を占めました（それぞれ 3 試行の中央値）。一方、`dark-engine:render` の 1 回の中央値は約 34 ms です。

別区間で採取したトレースでも `UpdateLayoutTree` が合計 1,386 ms、最長 205 ms と突出しています。同期処理の計測が短くても、その後のスタイル再計算によって長い停止が生じることと整合します。セレクターの照合方式など、さらに低い層の計算量までは特定していません。

`dark-engine:render` はこの同期処理の末尾で記録するため、処理後にブラウザが行うスタイル再計算を含みません。README の説明にこの制約を追記しました。過去の公開サイト確認で記録した「変換時間」は、操作全体の負荷や応答性を保証する値としては使えません。

静止中にも 1.5 秒ごとに CSSOM の文字列化と Shadow DOM の探索がありますが、制御ページの静止区間では全走査は発生せず、今回の大きな遅延の主因ではありませんでした。

[src/engine/sheets-canvas.ts](../../../src/engine/sheets-canvas.ts) は Sheets の Canvas 描画ごとに対象判定と色変換を行います。OFF でもラッパー自体は残ります。公開 Sheets の ON/OFF 比較では DOM 処理と Canvas 処理の両方が変わるため、Canvas 単独の寄与は分離できません。

## 公開サイト

以下の実サービスを OFF → ON → OFF で開き、各回は新しい一時プロファイルを使いました。公開サイトは内容や DOM が変わるため、この実行の観測値です。制御ページのような各モード 3 回の反復ではありません。

| 対象                                                                                                                    | マウス移動の所要時間 OFF（前 / 後） |       ON | 静止区間のタスク時間 OFF（前 / 後） |       ON |
| ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------: | -------: | ----------------------------------: | -------: |
| [Wikipedia / Color](https://en.wikipedia.org/wiki/Color)                                                                |                    2,330 / 2,322 ms | 7,491 ms |                          77 / 66 ms | 2,586 ms |
| [公開 Google Sheets サンプル](https://docs.google.com/spreadsheets/d/1BxiMVs0XRA5nFMdKvBdBZjgmUUqptlbs74OgvE2upms/edit) |                    2,338 / 2,337 ms | 2,329 ms |                          41 / 38 ms |   364 ms |

Wikipedia は約 4,800 要素で、ON の静止区間でも約 2.65 秒中 2.59 秒をタスクが占め、7 回の再走査がありました。マウス移動区間では 20 回の Long Task、フレーム間隔 p95 は OFF の 17 ms から ON の 367 ms へ増加しています。

Sheets は約 1,770 要素で、ON の静止区間でも 16 回の再走査がありました。処理時間は増えますが、この公開サンプルでは Long Task や操作列の所要時間の悪化までは確認できませんでした。読み取り専用のサンプルであり、個人の大規模シートや編集・数式入力は測定していません。

ホイールイベント 12 回の区間も JSON に記録していますが、移動距離を検証していないため、スクロールの正しさや完了の保証には使いません。測定対象はトップフレームです。別フレームで動く拡張の処理は集計していません。

表示の確認画像: [Wikipedia ON](wikipedia-on-1.png)、[Sheets ON](sheets-on-4.png)。

### 放置中の再走査の切り分け

`--diagnose` でマウスを動かさずにイベントと DOM 更新を記録しました。Wikipedia の ON では約 5.13 秒に `transitionend` が 1,005 回、再走査が 14 回あり、DOM 変更はありませんでした。色と境界線色のトランジションが、Wikipedia のラジオボタン・検索欄などで繰り返されています。OFF の約 5 秒では、これらのイベントも再走査もありません。

続けて同じ ON のページで、`window` の capture リスナーから `transitionend` の伝播だけを止め、1 秒の待機後に約 4 秒を測定しました。再走査は 0 回となり、タスク時間は区間全体の約 97% から約 3.5% に下がりました。

Sheets の ON でも約 5.02 秒に `.docs-menubars` の `color` の `transitionend` が 31 回、再走査が 31 回あり、DOM 変更はありませんでした。経路の遮断後は約 4 秒で再走査が 2 回となり、残った更新は共同閲覧者の DOM 変更・画像読み込みに対応していました。OFF の約 5 秒では、イベント・再走査ともに 0 回でした。

この結果と、スタイルシートを無効化・再生成・有効化してから `transitionend` でも再走査するコードから、拡張自身の配色再適用が次の再走査を誘発していると判断します。診断時のイベント遮断はサイト側のリスナーにも影響するため、製品の修正案や通常状態の性能値としては扱いません。本番コードには入れていません。

診断記録: [Wikipedia ON](wikipedia-on-feedback.json)、[Wikipedia OFF](wikipedia-off-feedback.json)、[Sheets ON](sheets-on-feedback.json)、[Sheets OFF](sheets-off-feedback.json)。最初のイベント観測は [idle-diagnostics.json](idle-diagnostics.json) にも保存しています。

## PC 側で観測した別の要因

調査開始時には CPU の空きが約 4%、スワップ使用量が約 12.6 GB でした。一方、13:07 頃の再確認では CPU の空きが約 74% に戻っており、PC の負荷は変動しています。これらの値だけから、拡張が PC 全体の負荷を生んだとは判断できません。

13:08 頃に結果保存が `ENOSPC` で失敗し、`df` では約 1.8 TiB のデータボリュームに空きが約 300 MiB しかありませんでした。容量不足は実際に確認できた環境上の問題です。今回、ディスク使用量の発生源は特定しておらず、利用者のファイル削除やアプリ終了は行っていません。

## 改善する場合の優先順位

以下は調査に基づく提案であり、実装済みの変更ではありません。

1. 拡張自身の配色再適用によるトランジションが、次の再走査を予約する自己ループを止める。サイト本来の状態変化への追従を保つ必要があり、イベントを全面的に遮断する診断処理をそのまま製品に入れない。
2. 操作ごとの全シート無効化・全置換を減らす。変換結果が同じ場合の CSS 再適用を避けるだけでなく、元の色を読むための全体無効化も対象にする。
3. DOM の変更箇所と、hover / focus による状態変化の影響範囲を管理し、全要素の再解析を必要な更新に絞る。継承・疑似要素・Shadow DOM の追従を壊さないことを既存の表示テストでも確認する。
4. 同期関数の時間だけでなく、操作列、Long Task、スタイル再計算を同じ条件で再比較する。関数の呼び出し回数や、環境次第の固定時間しきい値だけをテストの合否にしない。
5. DOM 側を改善後、Sheets の実操作で残る負荷を調べ、必要なら Canvas の対象判定・色変換を個別にプロファイルする。

# 別のターミナルや Chrome で http://127.0.0.1:4175/?cards=600 を開く
